DEKA ERP Architecture

One hosted system that runs sales, invoicing, purchasing, stock, accounting, logistics and people for many client companies. Each company sees only its own data and switches on only the modules it uses.

A shared core with modules per company

System architecture

The components that run DEKA ERP in production and how they connect. On a phone, scroll the drawing sideways.

Solid arrows carry live traffic; the dashed arrow is a release: each one updates the database and permissions, then switches over.

Hosting

Laravel Cloud runs the application and its scheduler; releases come from GitHub.

Application

Laravel 13 on PHP 8.4. The staff workspace is Filament 5 with Livewire 4; the API uses Sanctum keys.

Modules

30 plug-in modules on one core, each with its own screens, rules, permissions and tests.

Data

PostgreSQL managed by Supabase; files in S3-compatible storage, one folder per company.

Stack: PHP 8.4 · Laravel 13 · Filament 5 · Livewire 4 · Tailwind 4 · PostgreSQL · Pest tests.

Keeping client companies apart

Clients are unrelated businesses, so isolation is built into the data layer rather than into individual screens. The same rules hold in the browser, on the phone and through the API.

Automated tests attempt exactly the refused path, reading and writing another company's data, and must be turned away.

Every record belongs to a company

Stamped on creation; lines inside a document take their parent's company.

Every read is filtered

The database query itself is limited to the current company: screens, reports, exports and API alike.

Every write is checked

Saving into a company the user does not belong to is refused, from any screen or API call.

Every action needs a permission

Roles decide who may view, create, change or delete per module; modules a company has not taken are closed.

Every change is recorded

An activity log shows who changed or deleted what. Support access to a client account needs a reason, ends after 60 minutes and is logged.
