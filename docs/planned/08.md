# DEKA ERP — MASTER ACCOUNTING SYSTEM AUDIT, BENCHMARKING, VALIDATION AND IMPROVEMENT PLAN

## PROJECT OBJECTIVE

Conduct a comprehensive technical, functional, financial, operational, and regulatory audit of the existing DEKA ERP Accounting module.

The goal is to transform the accounting system into a reliable, professional, accurate, user-friendly, and commercially competitive accounting solution suitable for small, medium, and growing businesses.

DEKA ERP is a Laravel, Filament, and PostgreSQL-based SaaS ERP with company-level data isolation and modular ERP functionality.

The system is being piloted in Ghana, Zambia, and the Democratic Republic of Congo.

The Accounting module must integrate correctly with other activated ERP plugins.

We want to establish whether the current accounting engine is financially correct, operationally complete, easy to use, secure, scalable, and capable of supporting the requirements of professional accountants and businesses.

**This is not simply a UI redesign. It is a complete review of accounting correctness, data integrity, financial controls, transaction processing, financial statements, integrations, taxation, and usability.**

You must research, compare, verify, test, document, and improve the existing system.

Do not begin by rewriting the code.

First understand what already exists and how it works.

# PHASE 5 — GENERAL LEDGER AND DOUBLE-ENTRY ACCOUNTING

This is the highest-priority technical investigation.

Determine whether DEKA has a robust centralized General Ledger.

Every financial transaction must create the appropriate balanced accounting entries according to its transaction type and configured accounting policy.

## Required Posting Rules

- Total debits must equal total credits for every posted journal entry.
- Posted entries must be traceable to their source documents.
- Draft entries must not affect posted financial balances.
- Posting must be atomic.
- Failed posting must not leave incomplete financial entries.
- Duplicate posting must be prevented.
- The system must support safe corrections and reversals.
- Posted entries must not be silently deleted or modified.
- Adjustments must preserve transaction history.
- Accounting periods must be respected.
- Tenant isolation must apply to every ledger record.

Investigate the treatment of:

- Posting date
- Document date
- Fiscal period
- Journal type
- Reference number
- Currency
- Exchange rate
- Debit and credit values
- Source document
- Posting status
- Reversal relationships
- User identity
- Approval history

## Example Accounting Tests

Test an invoice for GHS 1,000 excluding tax.

- Revenue: GHS 1,000
- VAT: GHS 150
- NHIL: GHS 25

- Accounts Receivable: GHS 1,200

Validate the exact accounting treatment with the applicable configuration and regulatory rules.
